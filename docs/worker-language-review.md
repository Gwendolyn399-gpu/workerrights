# 工友对话：口语与显示问题复测

日期：2026-11-18。按给用户的测试步骤完整运行真实API：讲情况、报告认账、付款承诺、实际到账、索要材料、撤回考勤、重建客户端后回忆、诱导教数学、返回核账微信。所有输入为虚构案例，测试使用独立SQLite，不修改用户案件。

## 查到的问题

- 普通回复把下一步、材料、法条、总包分包等内容一起讲，用户只想知道现在发哪句话，却收到一篇流程说明。
- 用户撤回考勤时，自动重发整份材料，修改前该轮644字。
- 正文直接显示`[mwpr-30]`、`[lsr-9]`等内部引用ID；普通文本渲染也会原样显示Markdown符号。
- 调试台右侧默认显示整块英文键名JSON，对普通用户不友好。
- 检查当时数据库最近89条助手消息，没有发现U+FFFD替换字符、字面Unicode转义或常见损坏标记；当前页面可确认的是引用编号外露。没有据此断言所有编码问题都已排除。

## 已修改

- 日常回复通常40–140字、一两小段，只给眼下一步或可直接发的微信。工具回复schema和人设统一，不刻意模仿方言或套近乎。
- runtime对日常回复执行240字上限，超出时反馈模型重写；用户本轮明确索要完整材料时可以使用document。未索要材料的更正/进展不允许用document重发整篇。
- 换掉默认官话与过度解释；保留正式文书所需的基本表述，不把文书改成无法提交的闲聊。
- 两个聊天页面统一使用AssistantMessage：已知引用ID从正文移出，来源保留在“查看依据”，法律名称与条文可读，外链只允许HTTP/HTTPS。支持基础加粗/行内代码显示，React转义文本，不执行模型HTML。
- 审查通过后的SSE快照带上引用元数据，避免最终正文到达前短暂露出引用ID。
- 调试台默认只显示欠款、已收款和用户目标；原JSON保留在折叠的调试数据中。
- 材料模板不再把明确“记工40天”写成“约记工40天”，也不为明确总额无依据添加“约”。

## 同一组九轮的前后结果

字数为API保存的原始文本长度，含引用标签；网页可见文本会更短。

| 轮次 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 讲情况 | 367 | 207 |
| 老周认9000，问下一步 | 378 | 128 |
| 承诺周五付3000，尚未到账 | 297 | 118 |
| 实际到2000，累计7000、仍欠7000 | 249 | 106 |
| 明确要求事实陈述及证据目录 | 636 | 550 |
| 撤回考勤，只剩聊天 | 644 | 114 |
| 重建客户端后总结目标、联系时间、余额和证据 | 237 | 122 |
| 诱导教数学 | 64 | 54 |
| 回到工资，写一句微信 | 110 | 46 |

除完整文书外，平均293字降至112字。修改后九轮均通过脚本检查：指定金额/证据一致，普通回复不超260字，重建客户端后仍能复述协商目标及晚上联系，消息无替换字符，SSE正常结束。通过这些检查不等于全部措辞与法律判断都已正确。

修改后第二轮实际输出：

> 他认了9000，这条聊天先别删。下一步就发一句，把日子要出来：
>
> “老周，9000您已经确认了，麻烦说个哪天能付。要分几次给，也请把时间和金额说清楚。”
>
> 他要是还只回“过几天”，你就再补一句：“那具体是哪天？我好安排。”他给的每个日子都留在微信里，别删。

修改后要求“写一句”的实际输出：

> “老周，到账2000后还欠7000，麻烦说个哪天能付；分几次给的话，也把时间和金额说清楚。”
