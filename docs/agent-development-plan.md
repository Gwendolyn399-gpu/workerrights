# 工友权益助手 Agent 开发计划与 GitHub 调研

日期：2026-11-17。状态：调研与计划；尚未接入真实模型、安装新框架或验证第三方项目在本机运行。

## 1. 推荐结论

在现有 FastAPI/Pydantic/Python 项目内，先做一个负责对话的主 Agent，配合事实校验、法律检索、材料生成等工具和显式案件状态。保留现有可用规则，逐步替换机械问答。五个业务职责不必对应五个独立模型循环。先跑通实际咨询，再根据真实问题决定是否引入 Pydantic AI 或 LangGraph。

目标场景仍是河南建筑工地欠薪。用户可以自由描述、插问、纠正、不知道、稍后继续；系统能给出基于事实与来源的说明，并帮助整理可核对材料。范围不包括代用户提交政府投诉。

## 2. 当前代码起点

- backend/agents/provider.py 只定义 polish_statement，现有业务没有调用；配置云端 Provider 不等于对话已经使用模型。缺 Key 时会回退 Mock，未来应改为明确区分配置错误、规则模式、真实模型调用成功。
- backend/agents/orchestrator.py 已拆分接待、法律检索、分析、计划与表单职责；目前编排与数据库 Session 耦合。
- 接待由规则抽取器与问题顺序推进，已有事实、消息、intake 状态可以复用。
- 后端已有 Pydantic、httpx、SQLAlchemy，无须为了第一轮模型接入先增加大型平台。
- 现有 /cases/{id}/messages 是可优先保留的集成入口；具体返回格式须对照 serializers 与前端类型后与队友冻结。

## 4. Agent 应有的运行流程

1. 接收当前消息、近期对话、已确认事实、待核实事实、当前阶段；会话身份由后端控制，模型不决定访问权限。
2. 理解本轮意图：新增陈述、纠正、询问、跳过、要求生成材料、确认。
3. 产出结构化事实候选及对应用户原话；区分未提及、明确不知道、明确不存在、约数、冲突。来源片段必须能在对应用户消息中定位，不能只相信模型的 confidence。
4. 程序检查金额、日期类型及候选与原话的一致性；计算结果标明来源，不把三个月当具体日期，不将 3–6 个月取中点伪装成确定事实。
5. 当用户问法律或渠道时检索本地资料；仅从返回的资料 ID 引用，未核验资料不能升级为已核验。检索内容视为资料，不作为新的系统指令。
6. 简短回应当下问题，再提出一个最关键的追问。不要把“先填完所有字段”当作回答一般问题的前提。无需检索时不强行调工具。
7. 事实足够时邀请用户核对；确认后的事实修正应重新计算受影响结果，失效旧分析，而不是禁止用户自然纠正。
8. 根据确认事实与可用资料生成分析、证据缺口、优先行动和文书草稿，全部允许回看依据与修改事实。

核心分层：模型负责语言理解、候选提取与解释；程序负责访问控制、状态迁移、金额运算、来源 ID 检查和数据保存。结构校验通过不等于法律正确。

## 5. 与队友的交付约定（建议稿，待核对现有接口）

你负责 Agent 内部逻辑、模型配置、Prompt、工具调用策略和评测。后端队友负责 HTTP、案件权限、数据库提交、导出与部署。前端队友负责展示。法律资料的内容核验由团队指定负责人，Agent 接入核验结果。

建议内部调用：run_turn(input) -> output；Agent 不自行创建新数据库、不直接写前端、不另建一套案件 API。

输入：当前用户消息、有限对话上下文、案件事实与其来源、事实版本、当前阶段。法律检索可通过后端提供的函数调用。

输出：reply、fact_proposals、conflicts、next_question、suggested_stage、citations、实际 provider/model、调用结果与 token 用量（服务端记录）。最终状态与事实更新由业务层校验并提交。

如后续增加流式输出，可约定 reply_delta、facts_updated、turn_completed、error 事件；未验证完整的事实候选不得作为已确认事实增量写库。首个版本可以非流式，界面显示真实等待状态。

先提供请求/响应示例给队友，前端可用样例并行开发，后端按既有序列化结构适配。所有新字段是否公开给前端按实际需求确定。

## 6. 分阶段开发与验收

### M0：接口与固定评测案例（约半天）

阅读现有消息接口、序列化和状态调用路径，确定 Agent 的输入输出，制作 20 个虚构场景及预期事实、错误禁区和追问方向。输出接口说明、样例 JSON 与案例文件。队友可开始使用样例，不必等待模型接入。

### M1：真实模型最小对话（约 1 天）

使用已有 httpx 接入选定的兼容 API，从服务端本地配置读取 Key；不提交密钥。先做终端测试入口，支持多轮上下文，记录实际模型与调用用量。模型名、结构化输出和思考参数以接入时官方文档与接口测试为准。

验收：对同一事实的不同表达能够理解；“包工头把我拉黑了”等问题能得到上下文回应；缺 Key、余额不足、超时和模型失败可见，不用预制回复伪装真实 AI。先用虚构数据测试。

### M2：结构化事实与自然追问（约 1–2 天）

实现事实候选、用户原话来源、未知/约数/冲突状态及用户纠正；复用金额和地区规则作核对。替换固定顺序追问，保留必要的确认机制。完成服务端接口联调。

验收：一次给多项信息不重复问；“不是欠两万，是一万八”能修正并保留变更来源；“不知道项目名称”不会误改合同状态；明确没有证据和未询问证据不同；进度准确反映当前阶段。

### M3：可追溯法律检索（约 1–2 天，可与资料核验并行）

先改进现有中文关键词检索，按法律文件/条文组织引用和核验状态；检查固定注入核心法条是否挤占相关结果。每条建议关联适用事实和缺项。检索命中不足时再评估嵌入或重排，暂不为小知识库引入向量数据库。

验收：引用 ID 必须真实存在且与展示一致；无依据不编条号；国家与地区、版本及核验状态保持一致。来源不够时明确缺口，不能以大模型记忆伪装官方核验。

### M4：分析、行动与材料（约 1–2 天）

只展示当前事实支持的分析；行动按优先、可并行、需进一步咨询区分；文书从确认事实生成，模型可辅助表达，程序核对金额、日期、主体、占位符。事实修改后刷新受影响结果。

验收：仅有时长时写“工作约三个月，具体起止日期待补充”；无合同不等于无法维权，也不自动推出所有赔偿；页面、复制与导出内容一致；可辨认待补充部分。

### M5：端到端体验与发布适配（约 1–2 天）

与队友测试消息、事实、来源、材料及错误状态；再加必要流式回复。后端负责会话保存，前端验证手机体验。核实 Qoder Sites 对 Agent 运行环境的支持；必要时独立托管 Python 后端，比赛允许性与团队确认，未验证前不写已可部署。

上述为工程估算，随 API 权限、资料质量和队友进度调整。先争取 2–3 个工作日跑通 M0–M2，之后逐步完善，不把所有阶段塞进一次大改。

## 7. 评测怎么判断“真的更好了”

固定覆盖：完整描述、口语与错别字、多轮补充、主动纠正、金额冲突、约数、只有时长、未知主体、无合同、无证据、已有投诉、确认后修改、超范围问题、要求保证结果、提示注入、API 故障、双会话隔离、长对话。

每个案例记录：必需事实提取正确率、无依据事实新增数、重复追问次数、事实纠正成功与否、引用有效与相关性、材料一致性、首响应/总耗时、token 和实际费用。语言体验人工评价是否理解当前问题、是否易懂、是否一次只问必要问题。

验收门槛：固定案例中没有新增虚假金额/日期/主体；引用可定位且不冒充核验；重要冲突必须暴露给用户；接口失败不冒充成功。指标是阶段目标，不代表已经达到，也不能推断所有真实案例无错误。

## 8. 第一轮明确不做

不自训练法律模型，不堆五个自主聊天 Agent，不新增独立记忆库，不全网采集法律，不先铺向量数据库，不让模型自动提交投诉。模型框架通过小实验选定，不同时引入多个重叠框架。
