# 工友权益助手三人分工与联调

适用范围为首期河南建筑工地欠薪。本文更新旧交接文档里“五 Agent 编排”的分工口径，按当前单主控 Agent 代码划分责任。下文的新增接口字段是待三人对齐的提议，现有接口可继续使用。

## 当前实现与目标架构

| 目标组成 | 仓库现状 | 本轮要补 |
| --- | --- | --- |
| 单主控 Agent | 真实对话已走范围判断、工具调用、答复审查和案件状态保存 | 主控对接结构化地区检索与路径服务 |
| 法律 RAG | 已有国家与河南资料、条款来源和核验状态。Agent 使用本地文字检索，传入查询词和条数 | 传入结构化地区及日期，过滤不适用资料，返回覆盖情况 |
| 维权决策引擎 | 已有独立案件分析和行动指南规则。聊天工具未调用同一套路径规则 | 把地区、案件事实和渠道匹配收为共享服务 |
| 专业工具 | 已有核账、证据清单、草稿、案件记忆等能力 | 地区与路径服务优先，附件解析可另排 |
| 业务工作流 | 已有对话、案件恢复、行动指南和填报页 | 让聊天、行动卡、依据和材料使用同一套后端结果 |

当前技术是 Next.js、FastAPI、Python 工具循环与 SQLite。首轮集成可以沿用现有实现，文本检索也可以作为 RAG 的检索层。

## 责任与交付

| 负责人 | 主责 | 第一份可验收交付 |
| --- | --- | --- |
| Agent 负责人 | 对话、人设、范围、追问、工具选择和结果转述。维护工具入参适配、业务场景回放和整体验收 | 用后端约定的结构处理地区未知、地区已知和本地渠道未核验三种情况，输出口语答复及结构化行动 |
| 后端队友 | 地区解析、法律资料和渠道、路径规则、API、入库与案件隔离。维护服务测试与联调样例 | 不调用 LLM 即可输入案件事实和地区，拿到可追溯的条款、路径候选、缺项和渠道状态 |
| 前端队友 | 案件、对话、地区确认、事实更正、下一步卡片、依据与渠道展示、材料复制/下载体验 | 用同一份 JSON 样例展示有渠道、待确认地区、渠道未核验等界面，然后接现有 API |

Agent 负责人维护 `backend/agents/agent_v1/` 中的人设、运行循环、边界和工具编排。后端维护 `backend/legal/`、`backend/rules/`、`knowledge/`、数据库和 HTTP 适配。现有 `action_planning.py` 可供后端复用。前端维护 `frontend/`。三人共同确认接口语义，后端主写契约和示例，Agent 和前端分别维护消费者。

## 后端队友的第一张任务单

1. **规范工作地点。** 复用河南现有区划和别名表，返回省、市、区县编码及识别状态。允许用户更正。把工地地点和居住地分开。具体管辖仍由业务规则按资料和事实判断。
2. **把法律检索和渠道查询做成共享 Python 服务。** 法律检索按主题、地区和日期处理国家与地方资料，区分可用、待核验或未覆盖。渠道维护单独目录，记录地区范围、事项、适用条件、官方来源和核验时间。选河南两个已有样例地区验证差异，正式入口以实际核验结果为准。缺数据时返回缺口，避免从行政区划推导窗口网址或联系方式。
3. **提供路径选择服务。** 输入案件事实和已解析地区，应用团队确认的业务规则。返回建议下一步、原因、仍缺的信息、可用候选渠道及证据或材料要求。聊天和原行动指南最终共享该服务，避免同一案件收到两套答案。
4. **保留案件接口并补齐契约。** 继续提供建案、读取、消息和 SSE。后端交付可跑的服务、种子数据、响应样例以及规则测试。首个联调版本可在同一个 FastAPI 进程内直接调用 Python 函数，现有 HTTP 路由供网页和独立验证使用。

已有检索文件是 `backend/legal/retriever.py`。现有 `search(query, top_k)` 对包含“河南”或“郑州”的查询做轻量加分，尚未用结构化区划过滤。区划基线是 `backend/rules/regions.py`，渠道基线是 `knowledge/official_channels/channels.json`。旧规则和数据可以从这些文件接着做。

## 先定两份契约

| 调用关系 | 建议输入 | 建议输出 |
| --- | --- | --- |
| Agent 调后端领域服务 | `topic`、结构化 `work_region`、`facts`、可选 `as_of` | `coverage`、`missing_fields`、`citations`、`next_action`、`channels`。来源和渠道都带自己的核验状态 |
| 前端调 FastAPI | 沿用 `case_id`、消息文本和 `X-Session-Id`。地区确认通过现有事实编辑路径接入 | 沿用 `case`、`assistant_message` 和 SSE。需要行动卡时，约定一个结构化字段承载经后端确认的动作及渠道 |

第一份契约表达“后端找到了什么、缺什么、接下来可做什么”。第二份契约表达“页面应该展示什么”。口语正文由 Agent 生成。渠道地址、核验状态和行动卡来自后端结构化数据。

## 并行开发与验收

1. 三人先锁定正常、缺地区、渠道待核验、服务故障四份脱敏样例。后端交付服务返回，Agent 和前端同时用这些样例开发。
2. 后端先用固定案件测检索和路径，关闭模型依赖。Agent 用相同的后端样例测试会不会瞎编渠道、会不会只问最必要的内容。前端用相同 API 响应样例做页面状态，之后切换真实接口。
3. 联调只跑一条完整主线，外加几个会改变行为的分支。主线为描述欠薪、确认工作地点、给出带来源的下一步、后续收到部分工资、刷新后继续。分支包括更正地区后旧行动失效、本地未覆盖、接口失败和跨案件隔离。
4. 先用固定结果回归，确认问题发生在检索、对话还是显示。接口稳定后再跑少量真实模型测试。当前 `scripts/evaluate-worker-journey.py` 已能用虚构数据、独立 SQLite 实测对话、SSE 和重开案件，无需浏览器。地区服务接入后，给脚本加“工作地点更正后，渠道跟着更新”的验收。

交付验收看三个结果。同一个案件地点变化时，推荐结果随已核验数据变化。资料缺失时，页面和回答表达同一缺口。主流程从用户原话到行动卡每一步都能独立重放。
