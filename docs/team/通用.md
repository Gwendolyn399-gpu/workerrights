# 工友权益助手 · 通用 Agent 交接与开发提示词

> 适用仓库：https://github.com/liuyike200811-maker/workerrights
> 版本：2026-11-17
> 用途：把本文件整份交给任意前端、后端或主 Agent 框架开发 Agent。开头只改 `ROLE`，其余按角色执行。

## 0. 只改这一行：声明你的角色

```text
ROLE: OWNER
```

`ROLE` 只能三选一：

- `OWNER`：项目负责人，主 Agent 框架搭建者
- `FRONTEND`：前端队友
- `BACKEND`：后端队友

修改后，只执行与 `ROLE` 对应的任务章节。其他角色章节只用于理解边界和接口，不要越权执行。

如果 `ROLE` 不明确，先停止并询问人类搭档，不要猜。

开始实际修改前，你的第一条回复必须先写清：

```text
ROLE: <你的角色>
我将只修改：<目录/文件范围>
我不修改：<其他角色范围>
第一步：<阅读/复现/验证计划>
```

不要同时执行三个角色的任务。

## 0.1 三个角色总表

| 角色 | 一句话理解 | 主责 |
| --- | --- | --- |
| `OWNER` | 负责“大脑和骨架”，不是只做审核 | 五 Agent 编排、接待状态机、Agent 间输入输出、API 契约、整体集成、最终验收与合并、产品/法律口径 |
| `FRONTEND` | 负责“用户看到和操作的一切” | 页面、移动端、信息层级、对话交互、事实编辑、进度展示、可访问性、复制/下载体验、前端测试 |
| `BACKEND` | 负责“事实、法律、数据和文书是否准确” | 后端领域实现、事实抽取、金额/工期、法律检索、分析、行动规划、填报数据、导出、数据库、API 实现、后端测试 |

## 0.2 角色边界

### 如果 ROLE=OWNER

你主责：

- 五个 Agent 的职责边界与编排；
- 接待状态机与追问顺序；
- Agent 之间的输入/输出契约；
- API 字段、响应结构与兼容策略；

- 法律/产品口径的最终确认；
- `README.md`、`.env.example`、最终 PR 合并与部署决策；
- 审查前端/后端 PR，拒绝跨目录和单方面契约变更。

你仍然要写框架代码，不是只审阅。建议主责文件：

- `backend/agents/orchestrator.py`
- `backend/agents/intake.py`

### 如果 ROLE=FRONTEND

你主责：

- 首页、案件列表、对话接待、案件分析、行动指南、填报辅助；
- 信息层级、移动端布局、触控、焦点、空状态、错误状态；
- 快捷回复、事实编辑器、进度呈现、法律来源入口；
- 把后端的“已知 / 未知 / 约数 / 待核验”如实呈现；
- 页面、复制内容、下载入口的一致性；
- `frontend/types/api.ts`；
- `tests/frontend/`；
- 前端 PR。

你不主责：

- 不修改 `backend/`、`knowledge/`、数据库、法律结论；
- 不重写接待状态机或 Agent 编排；
- 不自行判断法律是否适用、渠道是否一定受理；
- 不计算时效、赔偿金、胜诉概率；
- 不新增后端没有返回的事实；
- 不把本地规则引擎包装成真实 AI；
- 不接入付费 API、不部署、不上传真实案件。

### 如果 ROLE=BACKEND

你主责：

- `backend/services/`：金额、工期、事实、陈述、导出；
- `backend/legal/`：知识库加载与检索；
- `backend/rules/`：地区、证据；

- `docs/api-reference.md`；
- `tests/agent/`、`tests/legal/`、`tests/api/`；
- 后端 PR。

你不主责，除非 `ROLE=OWNER` 明确授权：

- 五 Agent 编排与职责边界；
- 接待状态机与追问顺序；
- Agent 间输入输出契约；
- `backend/agents/orchestrator.py`
- `backend/agents/intake.py`

- `backend/agents/provider.py`
- `backend/api/schemas.py` 中的请求/契约结构；

## 3. 当前阶段要解决的已知问题

以下问题可能已部分修复。开始前必须用代码和虚构案例复现，不要直接假设。

1. 进度可能在可选问题、最终确认之前显示 100%。
2. 只有工作时长时，正式陈述可能出现“本人于约三个月在……”。
3. 填报页可能声称“模拟真实填报顺序”，并把时长当成工作起止时间。
4. 行动指南可能写“按顺序做”，暗示必须串行。
5. 用户已说“没签合同”时，证据说明仍可能写“目前未确认存在书面合同”。
6. 官方入口按钮可能指向机构首页，却看起来像具体办理入口。
7. 法律援助、仲裁时效、先行清偿等措辞可能过于绝对。
8. 页面可能展示内部字段名，如 `labor_supervision`、`official_platform`、`hotline`。

虚构复现案例：

> 我在郑州金水区工地做钢筋工干了三个月，包工头老王招我，每天350元，工资共两万六，付了六千，还欠两万，没有签合同，有微信聊天和转账记录。

## 6. 共享 API 契约

### 6.1 当前主要接口

- `GET /cases/{id}`
- `POST /cases`
- `POST /cases/{id}/messages`
- `PATCH /cases/{id}/facts`
- `GET /cases/{id}/analysis`
- `GET /cases/{id}/action-plan`
- `PATCH /cases/{id}/action-plan/steps/{stepId}`
- `GET /cases/{id}/form-assistant`
- `GET /cases/{id}/export/{fmt}`
- `GET /legal/search`
- `GET /legal/documents`
- `GET /regions/henan`
- `GET /channels`

会话头：`X-Session-Id: <8–64 位字母、数字、下划线或连字符>`

### 6.2 可能新增的字段

- `progress.stage`
- `progress.core`：`{ done, total, known, unknown }`
- `progress.optional`：`{ done, total }`
- `progress.confirmed`
- `progress.ready_to_confirm`
- `steps[].priority`：`now` / `soon` / `parallel` / `professional`
- `steps[].parallel_group`
- `steps[].requires_professional`
- `steps[].entry_type`：`institution_homepage` / `verified_service` / `search_required`
- `evidence.contract_state`：`confirmed_none` / `unknown` / `owned`
- `platform.reference_notice`
- 字段状态继续使用 `ready` / `missing` / `verify` / `official_only`

### 6.3 契约规则

1. 新增字段必须增量兼容，保留旧字段。
2. 字段变更先由 `OWNER` 确认。
3. `BACKEND` 更新 `docs/api-reference.md`，给前端示例 JSON。
4. `FRONTEND` 更新 `frontend/types/api.ts`，做可选兼容。
5. 删除/重命名字段必须单独讨论，不能夹在普通 PR 里。

## 7. 角色专属任务

只执行与 `ROLE` 对应的章节。

### 7.1 ROLE=OWNER：主 Agent 框架与集成

#### 目标

在不破坏现有可运行版本的前提下，完成第二版 Agent 框架与接口契约，并集成前后端改动。

#### 任务

1. 审核五 Agent 边界：
   - Intake：一次一问、事实收集、确认；
   - Legal Research：知识库检索与来源；
   - Case Analysis：关系、证据、权利、风险、管辖；
   - Action Planning：步骤、渠道、期限、风险；
   - Form Assistant：字段整理与官方入口。
2. 明确并实现进度契约：
   - 核心事实；
   - 可选信息；
   - 已确认；
   - 未知/跳过不等于已核实。
3. 明确行动步骤契约：
   - 优先级；
   - 并行组；
   - 是否需要专业人士；
   - 入口类型。
4. 明确证据契约：
   - 已确认没有；
   - 尚不清楚；
   - 已拥有。
5. 明确填报辅助契约：
   - 字段结构待核验；
   - 只有时长时不能当起止时间；
   - 官方入口类型。
6. 集成前后端 PR：
   - 先合并后端增量字段；
   - 前端 rebase 后接入；
   - 用虚构案例做端到端验收。
7. 最终审核：
   - 法律措辞；
   - 隐私边界；
   - 不自动提交；
   - Mock 标识；
   - 不部署。
8. 更新 `docs/agent-workflow.md`、`docs/architecture.md`、`docs/api-reference.md` 中与契约有关的部分。

#### 完成标准

- 五 Agent 职责清晰，没有巨型提示词；
- 新增字段有文档和示例；
- 前后端使用同一虚构案例通过；
- 法律措辞无绝对承诺；
- 测试全部通过；
- PR 不含敏感内容。

### 7.2 ROLE=FRONTEND：前端体验与真实性

#### 目标

把当前“能跑通”的原型打磨成真实用户容易上手、评委能体验完整闭环的前端。

#### P0 任务

1. 进度语义：
   - 核心事实已收集；
   - 可选信息待补充；
   - 信息是否已确认；
   - 100% 不代表全部完成；
   - 没有新字段时基于 `progress.checks` / `intake.unknowns` / `status` 保守降级。
2. 对话接待：
   - 允许先自由描述；
   - 快捷回复只对应当前问题；
   - 支持“不知道/稍后补充/跳过”；
   - 显示识别出的事实，可修改；
   - 已明确的信息不重复问；
   - 保留用户原话。
3. 首页：
   - 服务地区 → 能得到什么 → 开始咨询 → 虚构案例；
   - 减少重复入口和技术术语；
   - 手机端无溢出、按钮可点、输入区不被遮挡。
4. 分析页：
   - 先讲“你说了什么/还不清楚/建议/证据”；
   - 再展开法律依据；
   - 区分事实、推断、待核实、一般提示。
5. 行动指南：
   - 标题改为“建议优先做”；
   - 显示现在做/可并行/需专业判断；
   - 没有后端字段时不要虚构分组；
   - 不计算时效；
   - 官方入口区分首页与具体入口；
   - 不展示内部字段名。
6. 填报辅助：
   - 改为“欠薪材料整理参考”；
   - 不声称“模拟真实填报顺序”；
   - 只有时长时不填起止时间；
   - `ready`/`official_only` 才计可用；
   - 身份证等保持“仅官方填写”。
7. 证据状态：
   - 没签合同显示“已确认未签”；
   - 未知显示“尚待核实”；
   - 有合同显示“已有”；
   - 解释替代材料。
8. 可访问性与移动端：
   - 触控区域、键盘焦点、对比度；
   - `prefers-reduced-motion`；
   - 不凭截图声称无障碍合规。

- 复制失败提示；
- 导出失败提示；
- 长文本不溢出；
- 前端测试；
- 保持纯文本渲染。

- 页面、复制、导出一致；
- 手机/桌面实际检查；
- `npm test`、`npm run build` 通过；
- 控制台无错误；

#### P0 任务

1. 正式陈述时间表达：

```bash

```

### 8.4 开发中同步

```bash
git fetch origin
git rebase origin/main
```

fork：

```bash
git fetch upstream
git rebase upstream/main
```

### 8.5 提交前检查

```bash
git status
git diff
git add <只添加你修改的文件>
git diff --cached --stat
```

禁止提交：

- `.env`
- `workerrights.db`、`test_workerrights.db`
- `.venv/`
- `node_modules/`
- `.next/`
- `__pycache__/`
- 导出的 DOCX/PDF/TXT
- 真实用户数据、密钥、令牌

提交信息示例：

```bash
git commit -m "feat(frontend): clarify intake progress"
git commit -m "fix(backend): correct duration-only statements"
git commit -m "feat(agent): define structured progress contract"
```

### 8.6 推送与 PR

```bash
git push -u origin <你的分支>
gh pr create --base main --head <你的分支> \
  --title "<类型>: <简短说明>" \
  --body "## 改动\n- ...\n\n## 验证\n- ...\n\n## 兼容性\n- ...\n\n## 需要确认\n- ..."
```

fork 时：

```bash
gh pr create --repo liuyike200811-maker/workerrights \
  --base main \
  --head <你的用户名>:<你的分支>
```

### 8.7 冲突

```bash

git rebase origin/main
# 手动解决
git add <已解决文件>
git rebase --continue
git push --force-with-lease
```

不要对 `main` 强制推送，不要 `git reset --hard` 丢弃队友工作。
