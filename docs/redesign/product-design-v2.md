# 第二阶段 · 产品设计 v2

> 日期：2026-11-19  
> 上游依据：`docs/redesign/product-audit.md`  
> 状态：产品结构已确认；视觉方向已确认为 B + A + C（读本骨架 + 案卷事实 + 行动路线），详见 `DESIGN.md` 与 `docs/redesign/visual-directions.md`。本文件固定产品结构、内容契约和验收标准。  
> 约束：不新增半成品功能，不把演示数据当真实数据，不自动向政府平台提交，不承诺结果。

## 1. 一句话定义

**工友权益助手，帮河南建筑工地被欠薪的工友，用大白话把事实说清、证据备好、材料填好，并知道下一步去哪个官方渠道。**

不是“法律百科”，不是“自动投诉工具”，也不是“法律意见生成器”。

## 2. 产品定位

### 2.1 用户真正的问题

工友遇到的通常不是“没有一条法律”，而是：

- 不知道该先找谁、后找谁；
- 说不清时间、金额、招工主体；
- 手里有聊天记录和转账，却不知道哪些有用；
- 看到官方表格不知道每个字段填什么；
- 担心说错、写错、被推诿，或者被假中介骗。

### 2.2 产品提供的价值

把“说不清、不会写、不知道找谁”整理成一条可执行的路径：

1. 用一次一个问题，把事实整理成可核对的案件档案；
2. 把事实对照公开法规，标出可能相关的依据与证据缺口；
3. 把下一步拆成可勾选的行动步骤；
4. 把官方填报所需内容整理成可复制的参考；
5. 始终由用户本人核对、决定和提交。

### 2.3 核心任务

**让用户从“我很乱”走到“我知道今天先做哪一件事，手里带着什么材料”。**

### 2.4 目标用户与场景

**主要用户**

- 河南建筑工地被欠薪的工友，以钢筋工、木工、瓦工、杂工等为主。
- 可能年龄偏大，法律术语不熟，手机操作一般，处于焦虑和防备状态。
- 常在工地、宿舍、家中使用手机，可能光线强、网络一般、只用一只手操作。
- 可能由工友、子女或老乡代为操作，但最终必须由本人确认。

**次要用户**

- 演示与评审者：需要一个可完整体验的虚构案件。
- 开发者：`/agent-lab` 调试台，不属于普通用户产品面。

### 2.5 设计原则

1. **一次只做一件事。** 每屏只有一个主任务、一个主按钮。
2. **结论先行。** 先告诉用户“现在最该做什么”，再给依据。
3. **事实只有一个源。** 所有页面引用同一份案件档案，不各自维护一套说法。
4. **能核对，不替用户下结论。** 用“可能、需核实、以官方认定为准”，不用“肯定能拿到”。
5. **手机是主设备。** 390px 能完成核心流程，桌面只是增强。
6. **减少而不是增加。** 不为了“看起来丰富”堆卡片、统计数字和空洞文案。
7. **边界就在动作旁边。** 用户点“去官方平台”时，同时看到“由你本人提交”。

## 3. 范围

### 3.1 In scope（本期必须完整支持）

- 河南省 · 建筑工地欠薪。
- 匿名会话内的案件创建、对话、事实编辑、确认、分析、行动步骤、填报参考、导出。
- 本地规则引擎为默认路径；本地配置的真实模型为可选增强。
- 虚构演示案件。
- 法律资料来源、核验状态、免责声明、12348 / 12333 兜底。
- 移动端核心流程与桌面端完整流程。

### 3.2 Out of scope（明确不做）

- 河南以外的地区规则、其他行业欠薪、工伤、辞退、社保等完整办理。
- 账号、登录、跨设备同步、云端案件。
- 上传身份证、银行卡、聊天截图或证件照。
- OCR、自动识别图片、自动生成证据。
- 自动登录、自动填报、自动向政府平台提交。
- 代为投诉、代为仲裁、律师代理、胜诉或回款承诺。
- 通用法律聊天机器人、情感陪伴、社交功能。
- 支付、打赏、广告、推荐中介。
- 多语言、无障碍认证、离线 PWA（可作为后续增强，不作为本期验收项）。

### 3.3 半成品入口处理

未实现的场景不放入口。首页只展示河南建筑工地欠薪；其他情况用一句话引导到 12348 / 12333，不提供“敬请期待”的空按钮。

## 4. 成功标准

### 4.1 用户结果

- 用户能在 3 分钟内完成第一次有效陈述，并看到“已记下什么”。
- 用户能在确认事实后两屏内找到“下一步”。
- 用户能拿着行动步骤和填报参考，明确知道去哪个官方渠道、带哪些材料。
- 用户不会误以为产品会代替自己提交，或保证追回工资。

### 4.2 产品指标（验收时观察，不伪造数据）

- 核心流程完成率：开始 → 确认事实 → 打开分析 → 打开行动 → 复制/导出。
- 首问理解率：用户第一次回答后，系统是否记录到至少一个有效事实。
- 返工率：事实修改后，用户是否能发现并重新生成分析。
- 移动端任务完成：390px 无横向溢出，关键动作不被埋没。
- 法律边界：所有法律结论有来源/核验状态；没有“保证胜诉/一定能追回”的表述。

### 4.3 体验底线

- 移动端正文不小于 14px，元信息不小于 12px。
- 主要触控目标不小于 44 × 44px。
- 关键页面无控制台错误。
- 不依赖横向滚动才能读完关键内容。
- 页面支持键盘焦点、语义标题、可读的错误提示。

## 5. 信息架构

### 5.1 路由地图

| 路由 | 用户语言 | 单一主任务 |
| --- | --- | --- |
| `/` | 首页 | 开始一次整理，或打开演示 |
| `/cases` | 我的案件 | 回到一个案件，或新建 |
| `/case/[id]` | 对话 | 回答当前问题，核对事实 |
| `/case/[id]/analysis` | 案件分析 | 看懂“可能是什么、缺什么、先去哪” |
| `/case/[id]/action-plan` | 行动步骤 | 知道现在做哪一步，并勾选完成 |
| `/case/[id]/form-assistant` | 填报参考 | 逐字段准备官方平台所需内容 |
| `/agent-lab` | 开发调试台 | 仅开发者使用，不进入普通导航 |

### 5.2 导航命名调整

| 当前 | 建议 | 理由 |
| --- | --- | --- |
| 对话 | 对话 | 保持 |
| 案件分析 | 案件分析 | 保持 |
| 行动指南 | 行动步骤 | “步骤”比“指南”更像可执行任务 |
| 官方填报 | 填报参考 | 避免让用户以为产品会代为提交 |

### 5.3 进度模型

必须拆成两个独立概念，不能混用：

1. **信息完整度**：案件事实整理到多少项，例如 `已整理 11 / 11 项`。只描述信息，不描述办理。
2. **办理进度**：行动步骤完成了多少，例如 `已办理 0 / 8 步`。只在行动页或案件摘要中出现。

案件头部默认显示与当前页面相关的进度，并带明确标签；不显示裸的 `11/11`。

### 5.4 结果生命周期

```
新案件
  → 收集中（可对话、可修改事实）
  → 信息已确认
  → 分析/行动/填报可生成
  → 事实被修改 → 结果标记“需重新生成”
  → 重新生成后恢复为最新
```

事实修改后，所有派生页面必须显示统一的“信息已更新，以下内容需要重新生成”提示，并提供一个主按钮。不能静默展示旧结果。

## 6. 核心流程

### 6.1 新用户

1. 首页看到范围、主 CTA 和演示入口。
2. 点击“说说我的情况”，进入新案件对话。
3. 助手只问一个问题；用户用大白话回答。
4. 右侧/底部案件档案实时增加事实；未知项标“待核实”。
5. 信息足够后，助手提示核对档案；用户可编辑。
6. 用户确认后，看到“下一步：看分析”或“直接生成行动步骤”。
7. 分析页给出结论、证据缺口、渠道。
8. 行动页按阶段展示步骤，用户完成当前步骤。
9. 填报页逐字段复制，用户本人去官方平台提交。
10. 用户可导出 DOCX/PDF，或回到案件继续。

### 6.2 回访用户

1. “我的案件”显示案件、更新时间和“下一步”。
2. 打开案件后，头部显示当前状态；如果是“结果已过期”，先提示重新生成。
3. 用户可继续对话、补事实、修改档案、查看行动步骤。

### 6.3 演示用户

1. 首页“先看演示案件”进入一个完整虚构案件。
2. 每个页面持续显示“虚构演示”提示，不隐藏。
3. 演示案件可编辑、可勾选、可导出，但所有数据仍标明虚构。

## 7. 页面规格

### 7.1 首页

**主任务**：让用户开始，或先看演示。

**内容顺序**

1. 范围标识：`河南 · 建筑工地欠薪`。
2. H1：`工资被拖欠了？慢慢说，我们先把事实理清。`（候选，第三阶段可微调）
3. 一句解释：不用先懂法律，一次问一个问题，整理事实、证据、行动步骤和填报参考。
4. 主 CTA：`说说我的情况`；次 CTA：`先看演示案件`。
5. 三项信任事实：不要求身份证号 / 仅本浏览器会话可见 / 不代替提交。
6. 四步路径：说情况 → 补事实 → 看分析 → 照着办。
7. 范围与兜底：河南建筑工地欠薪；其他情况拨打 12348 / 12333。
8. 官方来源页脚。

**不要**

- 不放假的产品截图、假数据、统计数字条。
- 不把演示入口做成与主 CTA 同等权重。
- 不写“AI 帮你赢回工资”一类承诺。

**移动端**

- 首屏必须看见 H1、解释、主 CTA。
- 四步路径可在一屏半内读完。
- 无横向滚动。

### 7.2 我的案件

**主任务**：回到一个案件，或新建。

**内容顺序**

1. 标题、说明（匿名会话绑定）。
2. 主 CTA：`开始整理`；演示入口降为文字链接或次要按钮，只出现一次。
3. 案件列表：标题、状态、地点/工种/欠薪、信息完整度、更新时间、`下一步：…`、继续按钮。
4. 删除入口放在行尾菜单，二次确认；说明删除范围。
5. 空状态只保留一组开始/演示动作，不重复页面顶部按钮。

**状态**

- 加载：骨架或轻量 spinner。
- 空：一句话说明会得到什么，一个主 CTA。
- 错误：说明本地后端是否启动，提供重试。
- 有案件：按更新时间倒序。

### 7.3 对话

**主任务**：回答当前问题，核对事实。

**桌面结构**

- 左：对话区，占主要宽度。
- 右：案件档案，300px 左右，吸顶。
- 头部：案件标题、虚构标记、当前进度（带标签）、返回、新建。

**内容顺序**

1. 对话历史。
2. 当前问题或确认提示，视觉上突出。
3. 信息确认区：`已整理 11/11 项`、`请核对案件档案`、`确认信息`。
4. 确认后：`下一步：看分析`（主）、`直接看行动步骤`（次）。
5. 输入区：文本框、发送、可选语音；错误就地显示。
6. 底部：服务商/规则引擎标识、法律资料与不自动提交提示。

**助手消息规范**

- 每条消息有轻量“助手”标识，避免用户误认成官方。
- 先回答/追问，再解释；不写长法律课。
- 目标 40–140 字，最多 240 字；一次只问一个问题。
- 引用放在“查看依据”折叠区；没有引用时不虚构。
- 不用“你应该起诉”“你一定能拿到”这类结论。

**案件档案**

- 唯一事实源。包含地点、工种、时间、工资约定、已付、欠薪、合同、招用管理、已有材料。
- 未知值显示“待核实”，不自动补全。
- 支持编辑；编辑后触发结果过期标记。
- 提供“查看法律依据”。
- 不收集身份证号、银行卡号、证件照。

**移动端**

- 对话区占主要视口；输入区尽量保持在视口内。
- 案件档案改为摘要条 + 底部抽屉/全屏面板。
- 底部 tab 与输入区之间留安全区。
- 不把“案件信息”做成需要横向滚动的表格。

**失败与降级**

- SSE 中断：保留用户已输入内容，显示重试，不重复发送。
- 模型不可用：切换到本地规则引擎，或允许用户手动补事实；界面明确标注当前模式。
- 边界外问题：固定回复，引导 12348 / 12333；不把越界内容写入案件记忆。
- 紧急/安全风险：优先提示人身安全渠道，再处理欠薪事项。

### 7.4 案件分析

**主任务**：看懂“可能是什么、缺什么、先去哪”。

**内容顺序**

1. 标题、确认状态、信息完整度、导出。
2. **结论先行**（新增，最多三条）：
   - 你可能可以主张什么（用“可能、需核实”）。
   - 目前最关键的证据缺口是什么。
   - 建议先联系哪个渠道，为什么。
3. 用工关系链：只在信息足够时展示；不清楚时说明缺哪项事实。
4. 证据情况：已有、还需寻找、可替代、需核实；优先显示最影响下一步的 1–3 项。
5. 可能涉及的权益：核心诉求、需核实、条件未满足，配简短依据。
6. 法律依据：默认只显示 4 条，`展开全部`；每条有来源、核验状态、适用条件。
7. 需要特别注意：时效、合同、现金支付、包工头身份等。
8. 去哪里办：优先渠道、地址/线上入口、12333 确认提示。
9. 免责声明。

**不要**

- 不复述整张案件档案；只引用摘要并提供“核对档案”入口。
- 不默认展开全部 12 条法条。
- 不把“可能相关”写成“适用”。
- 不承诺“能追回”。

**移动端**

- 结论区必须在首屏或第二屏内出现。
- 提供页内快捷导航（结论 / 证据 / 权益 / 依据 / 渠道）或折叠分区。
- 长法条默认折叠。
- 底部保留“下一步：看行动步骤”入口。

### 7.5 行动步骤

**主任务**：知道现在做哪一步，并完成它。

**结构：3 个阶段，8 个步骤**

1. **先固定证据**：保存聊天、考勤、转账、照片、工友信息；不修改原始材料。
2. **把账算清楚**：工作日、单价、已付、欠付；时间线。
3. **找对渠道办理**：劳动保障监察、全国欠薪线索平台、12333、仲裁/法律援助/诉讼；说明哪些可并行。
4. **跟进与留痕**：受理编号、提交页面、沟通记录、后续程序。

阶段是阅读结构，不是强制锁定；用户可以展开任何一步。

**每步内容**

- 标题、为什么做、需要准备、可复制话术、期限/风险、相关官方渠道。
- 完成按钮 `标记完成` / `已完成`，触控目标 ≥ 44px。
- 当前建议步骤默认展开；其他步骤折叠但可见。
- 进度明确写 `办理进度 0 / 8 步`。

**顶部**

- 标题：`行动步骤`
- 一句说明：`先做这 3 件事；有些渠道可以同时准备。`
- 优先渠道卡：名称、理由、官方入口、12333 提示。
- 正式陈述只给摘要和“去填报参考查看全文”，不重复全文。

**不要**

- 不写“必须按顺序做完才能联系部门”。
- 不把时效与风险放到页面末尾；放到相关步骤旁。
- 不隐藏“这一步是建议，不是法律结论”。

**移动端**

- 首屏显示：当前阶段、当前步骤、完成按钮、官方入口。
- 折叠其他步骤。
- 目标：从页面顶部到当前步骤的操作不超过两屏。

### 7.6 填报参考

**主任务**：逐字段准备官方平台所需内容。

**命名与边界**

- 导航名：`填报参考`。
- 首屏第一句：`以下内容由你本人核对后，去官方平台填写和提交。本产品不登录、不代填、不自动提交。`
- 外链按钮：`去官方平台（本人提交）`。

**结构**

1. 平台名称、入口说明、来源/核验状态。
2. 进度：`15 / 18 字段可用`。
3. 步骤导航：7 步；移动端必须能完整到达所有步骤。
4. 当前步骤：目标、注意事项、字段列表。
5. 字段卡：含义、参考内容、来源事实、状态（可填写/待补充/需核对/仅官方填写）、复制。
6. 正式事实陈述：全文 + 复制。
7. 证据目录：材料、能证明什么、状态、获取方式；移动端改卡片。
8. 提交前核对清单。
9. 边界提示：不保存截图/证件照，不代替提交。

**移动端**

- 步骤导航用可横向滚动的分段条，带“第 1/7 步”文本和滚动暗示；或使用下拉选择。
- 字段不横向滚动。
- 证据目录不依赖 560px 表格；改为按材料分组的卡片。
- 正文不小于 14px。
- 底部 tab 不遮挡“下一步”。

## 8. Agent 产品契约

### 8.1 职责

Agent 负责：

- 接待与追问；
- 把用户原话整理成事实；
- 标记未知和冲突；
- 检索公开法律资料；
- 生成解释性回复；
- 在边界内组织材料。

Agent 不负责：

- 替用户下最终法律结论；
- 编造法条、链接、案例或证据；
- 自动提交；
- 承诺结果；
- 收集不必要的个人信息。

### 8.2 输出约束

- 一次一个主要问题。
- 目标 40–140 字，硬上限 240 字。
- 先结论/追问，后解释；不写长篇法条。
- 可能涉及法律时，使用“可能、需核实、以官方认定为准”。
- 引用必须来自知识库，带来源与核验状态；无来源时明说“需查证”。
- 被边界拒绝的回合，不写入事实、记忆或材料。

### 8.3 状态与记忆

- 事实补丁必须经过校验后提交；失败回合不污染案件。
- 用户修改事实后，派生结果标记过期。
- 记忆只保存与案件整理相关的内容；不保存敏感个人信息。
- 引用、运行 ID、用量只用于调试与可追溯，不展示给普通用户造成噪音。

### 8.4 模式标识

- 默认：本地规则引擎。界面标注“本地规则整理”或“演示模式”。
- 可选：本地配置的真实模型。界面标注服务商/模型名称，但不暴露密钥。
- 模型不可用：明确降级，不假装仍在用 AI。

## 9. 法律准确性与信任

### 9.1 必须遵守

- 法条、政策、官方入口只能来自知识库/配置，不由模型自由生成。
- 每条法律依据显示：文件名称、条款、来源、核验状态。
- 金额计算由确定性规则完成，模型只解释。
- 时效、管辖、程序性结论必须附“以官方认定为准”。
- 不承诺追回工资、胜诉、受理或赔偿。
- 不建议伪造、修改、补造证据；明确“缺少材料不等于不能维权”。
- 不引导用户向陌生人发送身份证、银行卡、验证码。
- 复杂、紧急、跨地区事项引导 12348 / 12333；人身安全风险优先提示紧急渠道。

### 9.2 文案禁区

- “保证”“一定能”“百分百”“包赢”“必拿回”。
- “官方合作”“政府指定”“代替你投诉”。
- “只要……就能……”的绝对因果。
- 把“公开文本未逐条核验”隐去，只显示结论。

## 10. 失败与降级矩阵

| 场景 | 用户看到 | 系统行为 |
| --- | --- | --- |
| 本地后端未启动 | 明确说明“无法连接本地服务”，提供重试 | 不伪造数据 |
| 模型超时/不可用 | `当前使用本地规则整理` + 重试/继续 | 保留已有事实 |
| SSE 中断 | `回复中断，可重试` | 保留输入，不重复提交 |
| 事实冲突 | `这项信息和之前不一致，请确认` | 不自动覆盖 |
| 分析/行动/填报生成失败 | 错误说明 + 重试 | 不清空案件 |
| 事实修改后结果过期 | `信息已更新，请重新生成` | 派生页标记 stale |
| 导出失败 | 就地错误 + 重试 | 不下载空文件 |
| 存储不可用 | `本次记录可能无法保存` | 不崩溃，允许继续当前会话 |
| 边界外问题 | 固定说明 + 12348/12333 | 不写入案件记忆 |
| 紧急安全风险 | 先提示紧急渠道 | 不继续普通欠薪流程 |

## 11. 内容与文案系统

### 11.1 语气

- 像一个有经验的工友/社工，不像法院判决书。
- 短句、动词开头、少术语；必须用术语时，紧跟一句大白话。
- 不居高临下，不吓唬，不承诺。
- 对未知坦诚：“这项还不清楚，可以之后补。”

### 11.2 标签

- 状态：`已确认`、`待核实`、`需补充`、`需重新生成`。
- 证据：`已有`、`还需要寻找`、`可替代或辅助`、`需进一步核实`。
- 字段：`可填写`、`待补充`、`需核对`、`仅官方填写`。
- 不用装饰性标签，不用“AI 智能”“一键搞定”等夸张词。

### 11.3 按钮

- 动词开头：`说说我的情况`、`确认信息`、`看分析`、`标记完成`、`复制此字段`、`去官方平台（本人提交）`。
- 一个区域最多一个主按钮。

## 12. 数据契约（产品层）

本期不直接改后端，但实施阶段需要满足：

- 一个案件有唯一事实快照和 `intake.confirmed`。
- 派生结果（analysis/action/form）能判断是否基于当前事实。
- 每条派生内容能追溯到事实字段或知识库条目。
- 渠道使用统一 ID 与统一来源数据，不在三个页面各写一套。
- Agent 回复、引用、材料、运行信息有结构化字段，前端不解析自由文本。
- 演示案件明确 `is_demo`，所有页面一致标识。

## 13. 验收标准

> 验收时使用真实浏览器截图与 PASS / UNVERIFIED 记录，不接受“代码看起来没问题”。

### 13.1 功能

1. 首页在 390px 和 1440px 均无横向溢出；首屏可见主 CTA。
2. 新建案件后，助手一次只问一个主要问题；回答后事实档案更新。
3. 刷新页面后，案件与事实仍在；删除后不可恢复且有确认。
4. 信息确认后，用户在两屏内能找到“看分析/看行动”。
5. 修改事实后，派生页面出现“需重新生成”，重新生成后消失。
6. 分析页首屏或第二屏出现三条结论；法律依据默认折叠。
7. 行动页显示 `办理进度 x/8`；当前步骤默认展开；完成状态刷新后保留。
8. 填报页 7 个步骤在 390px 可完整到达；证据目录不使用横向表格。
9. 复制字段、复制陈述、DOCX/PDF 导出可用。
10. 模型失败时可降级继续；不丢失已输入事实。
11. 网络面板中没有把身份证、聊天截图或证件照上传到第三方。
12. 页面不出现自动提交按钮或“保证追回”文案。

### 13.2 体验与无障碍底线

- 移动端正文 ≥ 14px，元信息 ≥ 12px。
- 主要触控目标 ≥ 44 × 44px。
- 键盘可到达输入、确认、步骤完成、复制、导出。
- 标题层级连续，表单有 label。
- 错误信息不只用颜色表达。
- 控制台无 error。

### 13.3 证据

- `1440×900`：首页、对话、分析、行动、填报截图。
- `390×844`：同五页截图，至少包含分析/行动首两屏和填报第 1/7、7/7。
- 记录 `scrollWidth`、页面高度、控制台错误。
- 记录一次完整流程：新案件 → 回答 → 确认 → 分析 → 行动 → 填报 → 导出。
- 记录模型失败/后端不可用的降级路径。
- 最终 QA 表使用 PASS / UNVERIFIED，不用“应该可以”。

## 14. 第三阶段需要决定的视觉问题

本阶段只固定产品，不固定最终皮肤。第三阶段将比较：

1. **案卷纸感**：吸收离线 HTML 的纸白/沙色/陶土色/衬线标题，强调“整理材料”的温度。
2. **冷静工具感**：保留当前蓝/纸白/无衬线，强调可信、克制、低认知负担。
3. **混合方向**：保留蓝色作为动作色，引入暖纸底、衬线标题和少量陶土强调，避免两个极端。

无论选哪个方向，必须满足：

- 移动端可读性优先；
- 不回到营销长页；
- 不用大圆角、渐变、玻璃拟态堆装饰；
- 不牺牲信息层级与法律边界。

## 15. 本阶段结论

v2 不是“把离线 HTML 搬进来”，而是把离线原型里正确的产品气质和内容结构，落到真实数据和真实失败路径上：

- 一个事实源；
- 两个进度概念；
- 三个阶段的行动；
- 四个任务面；
- 每个页面只回答一个问题；
- 每个结论都可核对；
- 每个动作都不越过“本人提交”的边界。

这将成为第四阶段重构计划的直接输入。
