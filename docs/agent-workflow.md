# Agent 工作流

## 1. 设计原则

1. **五个独立 Agent，而不是一个巨型提示词**：每个 Agent 只做一件事，输入输出可测试。
2. **事实由用户提供**：抽取器只记录用户说过的内容，缺项保持 `null/待核实`。
3. **法律结论来自知识库**：Agent 不凭模型记忆生成条文；检索结果附带元数据和核验状态。
4. **先问最关键的问题**：一次一个问题，根据已答字段动态跳过。
5. **不承诺结果**：使用“可能”“需核实”“建议咨询”等措辞。
6. **可修改**：事实编辑器修改后，分析与计划按新事实重新生成。

## 2. 编排器

`AgentOrchestrator` 持有：

- `IntakeAgent`：对话接待与事实收集
- `LegalResearchAgent`：法律检索
- `CaseAnalysisAgent`：案件分析
- `ActionPlanningAgent`：行动规划
- `FormAssistantAgent`：官方填报辅助
- `AgentProvider`：默认 Mock；云端润色适配器为预留

对话路径：`IntakeAgent.handle_message()` → 持久化 → 返回消息、下一问题、进度。分析与计划在对应 GET 请求时生成。

## 3. 接待 Agent（Intake）

### 3.1 问题顺序

1. 工作城市/工地（未识别城市时继续问具体位置）
2. 区县（可选；用于匹配受理机构，不假设每区县都有机构）
3. 工种
4. 工作时间/工期
5. 谁介绍/招用
6. 平时谁管理、记考勤
7. 工资算法（按天/按月/计件/包工价）
8. 金额（应发、已付、欠发；支持一句话多个金额）
9. 已支付金额（用于核对欠款）
10. 书面合同
11. 证据（多选，可“都没有”）
12. 欠款复核（应发 − 已付 与用户陈述对比）
13. 约定总额（可选补问）
14. 项目信息（可不知道）
15. 此前是否投诉/反映
16. 确认信息

“不知道/跳过”会记录到 `intake.unknowns/skipped`，不会反复追问同一项；必要时进入待核实。

### 3.2 事实抽取

`FactExtractor` 是确定性规则：

- 地点：城市/区县别名，支持“郑州金水”“兰考”等；
- 金额：阿拉伯数字、中文数字、口语“两万六”“两万三”“一天350”；保留约数；
- 工期：`3-6个月` 取中值 4.5 并保留原文；`不到1个月`、`半年`、`45天`；
- 招用/管理：区分包工头、劳务公司、项目部；不因“包工头介绍”就推断工资算法；
- 合同：只有明确“没签/签了/不知道合同”才写入；
- 证据：按目录识别聊天、考勤、工资表、转账、欠条、照片、工牌、工友、录音、合同；
- 项目：识别“项目叫/工地是”等表达；不能确定时不编造；
- 电话：仅在用户主动提供时保存，不主动索取。

安全保护：当用户回答“不知道项目名称”而当前问题问的是合同时，不会把合同误记为“不知道”（`_unknown_refers_elsewhere` 与抽取器双重约束）。

### 3.3 确认

必填字段完成后，系统复述应发、已付、欠发。用户说“信息无误，生成分析”后：

- `status=ready`
- `intake.confirmed=true`
- 后续普通消息不再改变关键事实，提示用户用“修改案件信息”。

## 4. 法律检索 Agent

1. 根据地点、工种、合同、证据、招用主体等构造查询。
2. 固定加载 12 条核心条文（工资支付、总包先行清偿、违法分包、监察、仲裁时效、法律援助等）。
3. 使用中文 bigram + BM25 风格打分检索最多 10 条。
4. 合并去重，最多返回 12 条；每条包含：
   - 法律名称、条文号、正文
   - 发布机关、文号、地区、生效时间
   - 官方链接、核验状态、核验标签
   - “为什么相关”
5. 返回 `verification_summary`，明确多少条待核验。

**不做**：不把模型生成的“法条大意”当条文；不给出脱离条文的胜负判断。

## 5. 案件分析 Agent

输出：

- `basic_info`：地点、工种、工期、金额、主体
- `relationship`：建设单位 → 总包 → 分包/劳务 → 包工头 → 劳动者；未知节点保留并标注
- `evidence_analysis`：已有 / 可补充 / 需要固定 / 暂缺，附获取方法
- `rights`：工资支付、未签合同可能的二倍工资（需核实劳动关系）、逾期赔偿金等
- `legal_analysis`：法律卡片
- `risk_flags`：主体、证据、时效、金额、关系复杂度
- `jurisdiction`：按项目所在地匹配；提示拨打 12333 核实具体机构
- `summary`：面向用户的行动摘要

复杂关系（总包/分包/包工头链条不清）会加入“建议法律援助/律师”的风险提示。

## 6. 行动规划 Agent

固定 8 步：

1. 固定证据
2. 核对工资总额与欠款
3. 通过微信请对方书面确认
4. 向项目所在地劳动保障监察投诉
5. 通过全国根治欠薪平台/12333/12345 反映
6. 视情况向住建部门反映
7. 申请劳动仲裁（注意一年时效）
8. 申请法律援助 / 诉讼准备

每步包含：为什么、准备清单、渠道、法律依据、期限、风险、可复制话术。

计划按事实签名缓存；事实变化时重建，并保留同名步骤的完成状态。

## 7. 填报助手 Agent

- 从 `knowledge/official_channels/root-wage-platform-form.json` 读取 7 步/18 字段。
- 逐字段生成：值、状态、说明、复制文本。
- 身份证号、姓名、银行卡等不在本产品收集，状态为“仅官方填写”。
- 生成正式陈述、简短描述、证据目录、复制摘要。
- 明确提示：字段结构待核验；不自动登录、不自动提交。

## 8. 模型适配层

```python
class AgentProvider(ABC):
    def polish_statement(self, draft, facts) -> str: ...
```

- `MockProvider`：原样返回，不调用任何模型；`is_mock=True`；UI 和 API 显示“本地规则引擎（演示，未连接大模型）”。
- `OpenAICompatibleProvider`：预留的 DeepSeek/OpenAI 兼容润色适配器，密钥只从服务端环境变量读取。

**当前流程未调用任何 `polish_statement`**。即使配置了云端适配器，事实、法条、计划仍由规则和知识库生成。启用云端润色前必须补充：用户明示同意、发送字段最小化、保留占位符校验、输出事实一致性校验。因此默认 `LLM_PROVIDER=mock`，文档不宣称已具备真实 AI 对话。

## 9. 失败与边界

- 消息为空：422。
- 会话无效：400。
- 跨会话案件：404（不暴露是否存在）。
- 不支持的场景：400。
- 大模型适配器缺少 Key 时回退 Mock，并在健康信息中显示 Mock。
- 事实值非法：400，不静默写入。
- 复杂或证据不足：提示补充/咨询专业人士，不输出保证性结论。

## 10. 示例

用户：

> 我在郑州金水区一个工地干了三个月，老板还欠我两万多。

系统识别：郑州市、金水区、3 个月、欠款约 2 万；继续追问工种、招用人、工资算法、应发/已付等，而不是一次抛出长表单。

确认后：

- 分析页展示总包先行清偿等条文，但注明需核实分包关系；
- 行动指南先固定微信/考勤，再投诉；
- 填报页给出欠款金额“2万元”，身份证号留空并提示本人填写。
